# Параметризовані SQL-запити

## Контекст
Нефункціональна вимога безпеки StudyFlow: «параметризовані SQL-запити, без виконання довільного вводу як коду» (`docs/app-requirements.md`). Назва, дисципліна, термін, ідентифікатор і фільтри надходять із командного рядка й потрапляють у SQLite-запити модуля `studyflow/storage.py`.

## Рішення
Усі значення від користувача передаються в `sqlite3` лише через плейсхолдери `?` і кортеж/список параметрів; текст SQL складається тільки з фіксованих рядків у коді.

## Поточна реалізація
- `add`: `INSERT INTO tasks(title, course, due) VALUES (?, ?, ?)` після `validate_task`.
- `list`: динамічний `WHERE 1=1` доповнюється лише константними фрагментами `AND course = ?` / `AND status = ?`, значення йдуть у `params`; `status` додатково перевіряється білим списком `open`/`done` до побудови запиту.
- `done`: `UPDATE ... WHERE id = ? AND status = 'open'`.
- `summary`: дата перевірки передається як `due < ?`.
- Схема має `CHECK (status IN ('open', 'done'))` як додатковий захист на рівні бази.

## Причина
Плейсхолдери відокремлюють дані від коду, тож лапки чи `;` у назві задачі не змінюють запит. Це стандартний механізм `sqlite3` без залежностей і зберігає відтворюваність.

## Альтернативи
- Форматування рядків (f-string, `%`, `+`) з екрануванням вручну — відхилено: легко помилитися, порушує вимогу безпеки.
- ORM (SQLAlchemy) — відхилено: зайва залежність для однієї таблиці й локального CLI.

## Наслідки
- Нові запити мають дотримуватися того самого правила; імена колонок чи порядок сортування не можна параметризувати через `?`, тому їх слід брати лише з білого списку.
- Редагування `storage.py` проходить через hook W1 (`ask`).
- План на майбутнє (ще не реалізовано): тест, що зберігає назву на кшталт `x'); DROP TABLE tasks;--` і перевіряє, що вона повертається без змін, а таблиця ціла.
